Ignition on the desktop

Can Terminal Delight's pane power-on/off flash play on the whole desktop, through omarchy-crt's screen shader? Another agent said it cannot. It can.

verdict

Possible, and most of the machinery already ships. The impossibility claim fails on three separate facts, each checked at the source: the effect needs no window pixels, Hyprland restarts a screen shader's clock every time one is applied, and omarchy-crt already rebuilds and swaps its shader on every window open and close without a single dropped frame of glass. The real compromise is small: the flash would begin a frame or three after the window changes, where Terminal Delight starts it on the same frame.

Read first

  • 1

    measured Hyprland restarts the shader clock on every apply. In the source of the exact version on this machine, applying a screen shader records an initial time, and the time uniform counts up from it. Swap a shader in and its animation plays from zero — no timestamp baking, no epoch math. This is the trigger primitive the impossibility verdict assumed did not exist.

  • 2

    measured The effect never touches the pane's pixels. Terminal Delight's ignition is white gradients over a dark ground — its own code says the curvature and scanlines "are not drawn here, they are what the tube does to whatever it is shown." So the strongest argument — that a closed window's content is gone before any shader could animate it — is true and irrelevant.

  • 3

    measured The trigger and the delivery already exist. omarchy-crt's watch rides Hyprland's event socket (openwindow, closewindow, movewindow…) and rebuilds the shader on each, and its two-slot swap was built precisely so that "there is no moment where the desktop is unglassed."

  • 4

    inferred The costs are latency and bookkeeping, not possibility. An estimated one to three frames between the event and the first flash frame, and some offset arithmetic in the watcher when a second animation starts while one is mid-flight. Neither is measured yet.

What the effect is

Terminal Delight calls it ignition: 300 ms, three movements. The phosphor floods in from the top and bottom edges and meets in the middle; the lit screen collapses to a single scan line; the line pinches to a four-pointed star that dies as the terminal comes up behind it. Shutdown is the same arc entered at the second movement — the screen closes to a line, the line pinches to a star, the vacated space shows through before the last light is gone. Everything is a function of the pane's rectangle and a normalised clock, drawn as plain quads and gradients. In GLSL that is a rect, a time, and three eased branches.

The impossibility, taken apart

"A screen shader cannot know a window closed"

measured The shader alone cannot — but the shader is not alone. omarchy-crt's watch holds a connection to Hyprland's event socket and rebuilds the shader on every event that can move, create or destroy a surface. A closing window already triggers a rebake today; the port adds content to a rebuild that already happens.

"There is no way to start a clock at the event"

measured Hyprland 0.56.2 — the version installed here, read at its release tag — records an initial time whenever a screen shader with a time uniform is applied, and feeds the shader global − initial. Every swap starts the clock at zero, so a one-shot animation is just a branch on time < 0.3 that folds to nothing once it has played.

Invalidation: if a live test — a swapped-in shader whose brightness ramps with time — shows the clock continuing rather than restarting, this finding falls and the port needs baked epoch offsets instead. Still possible, just uglier. One photographed test settles it.

"The closed window's pixels are gone before you could animate them"

measured True, and it does not matter. Terminal Delight's own ignition draws no window content: it is an emissive flash — white gradients — over an opaque dark ground whose opacity is what hides or reveals whatever sits beneath. The desktop version draws the same flash over the vacated rectangle. Nothing needs the dead window's texture.

"Reapplying the shader flashes the desktop"

measured It used to. The two-slot swap was built to kill exactly this: the new build lands under the path not currently live, Hyprland compiles it and switches, and the glass never drops for a frame. Triggered animation inherits that delivery for free.

"A time uniform murders performance"

measured Whenever any tube exists, the watch already runs with damage tracking off — the gather requires it — so the full-screen-redraw price is already being paid in the state where the animation would play. Hyprland's warning about the time uniform only fires when damage tracking is on. The clockless steady shader returns one more swap later, about a third of a second after the event, and that swap is as invisible as the first.

How it would run

  1. closewindow (or openwindow) arrives on the socket the watch already holds.
  2. The watch diffs the old rect list against the new one: a rect that vanished is dying, a new one is born.
  3. It renders the animated variant of the shader — the steady glass plus a dying/born rect array with per-rect phase offsets, clock declared.
  4. Two-slot swap. Hyprland compiles the new path, the clock restarts at zero, and the flash plays over the vacated (or newborn) rectangle.
  5. When the longest flash is over, the watch swaps the clockless steady shader back in — same invisible move.
  6. An event landing mid-flash re-bakes in-flight animations with negative start offsets so each keeps its place in its own arc. Pure bookkeeping, and the only genuinely fiddly part.

Decisions

1 · Build it?

The exploration says feasible; feasible is not the same as worth a day of work plus a live verification pass on your actual desktop.

Recommendation: yes — prototype behind an off-by-default service-panel knob. First milestone is not code that ships, it is a photographed answer to the clock-reset test, which is one throwaway shader and ten minutes.

2 · Shutdown first, or both halves at once?

Shutdown plays over empty desktop, so start latency and the compositor's own fade forgive it. Ignition plays over a window that is already visible, so the same latency shows as a raw flash before the dark ground lands.

Recommendation: shutdown first. Ignition follows once the latency number exists and says whether it needs a window rule to hide the pop-in.

3 · Whose feature is it?

The watcher, the two-slot swap and the knob panel all live in omarchy-crt; the theme's own shader is a sibling that syncs geometry from the theme via an established one-way channel.

Recommendation: omarchy-crt owns it. The theme inherits nothing unless we later decide the flash belongs in the theme's staged shader too, through the same sync.

The clock reset, at the source

Hyprland v0.56.2 · src/render/OpenGL.cpp · tag matches the installed build

When a screen shader is applied

if (m_finalScreenShader->getUniformLocation(SHADER_TIME) != -1)
    m_finalScreenShader->setInitialTime(g_pHyprRenderer->m_globalTimer.getSeconds());

Every frame it renders

shader->setUniformFloat(SHADER_TIME,
    g_pHyprRenderer->m_globalTimer.getSeconds() - shader->getInitialTime());

So the time a screen shader sees is seconds since this shader was applied, not since the compositor started. The two-slot swap forces a fresh apply (Hyprland will not recompile a path it is already using, which is why the slots alternate), so every swap is a clock reset. A one-shot animation needs nothing else.

The installed build is pacman's hyprland 0.56.2-1; hyprctl version reports the same tag, so the tag source read here is the code that runs.

Why the existing shader never noticed

The steady glass only uses the clock through mod(time, period) — the tracking band, the flicker window. Those are origin-independent, so a reset on every rebake was invisible. The reset only becomes observable — and useful — when an animation cares where zero is.

A bonus roster

The same file feeds screen shaders more than a clock in 0.56: pointer_position, pointer_pressed_times, pointer_shape and friends. Nothing in this port needs them, but a click-ripple or a cursor-reactive glass would be the same shape of project, with less machinery than this one.

The arc, dial for dial

terminal-delight · app/src/crt.rs · Ignition / shutdown

The published constants

  • IGNITION_MS = 300 — "punctuation on a new pane, not a cutscene"
  • BLOOM_END = 0.40 — the flood has met in the middle
  • COLLAPSE_END = 0.68 — the screen has closed to a line
  • ARM = 0.012 — thickness of the star's arms, as a fraction of the short axis

The three movements

  • Bloom — light floods from the top and bottom edges toward the middle, eased out (1−(1−p)²): the tube's brightness overshoots and settles. Glow ramps 0.35 → 0.8.
  • Collapse — the lit screen closes to a scan line, eased in (p²): slow to let go, then all at once. Glow reaches 1.0.
  • Pinch — the line shrinks horizontally while a vertical spike turns the dash into a four-pointed star; the star stays hot for the first half and dies at the end, while the ground opens up linearly underneath it — the reveal is under way before the light is gone.

Shutdown is one line

pub fn shutdown(t: f32) -> Option<Ignition> {
    ignition(BLOOM_END + t.clamp(0.0, 1.0) * (1.0 - BLOOM_END))
}

The power-down re-enters the same arc at the end of the bloom, so every guarantee the ignition carries — ordered phases, a ground that only opens, values in range — holds for free, and a change to the easing moves both. The GLSL port should keep exactly this shape: one arc, two entry points.

Why the port is small

The overlay draws plain quads and gradients inside the pane's tube — the terminal's own scanlines and curvature are applied by the glass on top of it, not drawn by the effect. In the desktop shader the same is true for free: the flash is composited before the scanline and vignette stages that already exist, so it inherits the glass exactly the way the terminal's version does.

The offset bookkeeping

the one genuinely fiddly part, worked through

The problem

Every swap resets the clock to zero — that is the feature. But if window A's shutdown is 120 ms into its arc when window B closes, the swap that starts B's flash also resets the clock A was reading. Unhandled, A's flash restarts from its beginning.

The fix

The watcher knows the wall-clock moment each animation began. When it bakes a new variant it writes each in-flight animation's elapsed time as a negative start constant:

// baked per dying/born rect, seconds relative to THIS apply
const float FX_START[FX_COUNT] = float[FX_COUNT](0.0, -0.12);
// in main(): float p = (time - FX_START[i]) / 0.3;  // 0..1 through the arc

B starts at 0.0; A, already 120 ms in, is baked at −0.12 and continues where it was. The shader never knows a reset happened. The watcher needs a small table of (rect, kind, started-at) that it prunes when arcs finish — a dozen lines of Python next to state the watch already keeps.

The exit swap

When the last entry ends, one timer fires and the watch applies the steady clockless build. If a new event lands first, the timer is simply superseded by the next rebake. Either way the steady state never carries a clock, so the damage-tracking posture stays exactly what it is today: off while tubes exist, on when the desktop is bare.

What is deliberately not done

No attempt to animate the window's real texture (a genuine Hyprland C++ plugin could, using the compositor's close-snapshots — different project, different cost), and no per-monitor special-casing: one shader serves all monitors already, distinguished by wl_output, and the flash rects carry their monitor the way tube rects do today.

What this exploration did not establish

method: source reads of running code — nothing was rendered

Not yet observed on a screen

  • The clock reset itself. Read in the release-tag source that matches the installed build, which is strong — but the house rule for renderer work stands: verified means photographed. A throwaway shader whose brightness ramps over three seconds, swapped in twice, settles it before any real code is written.
  • Start latency. The 30–100 ms figure is a guess assembled from hyprctl round trips, a Python render, an optional glslang validation and a swap. The watch prints on every refresh; timestamping one run under window churn gives the real number.
  • How the flash reads next to the compositor's own close animation. A taste question no source read answers.

Structural limits of the method

  • The repo claims (watch events, two-slot swap, damage-tracking posture) are reads of code that runs on this machine every day — high confidence, but its edge cases (a monitor hot-plug mid-flash, a Hyprland reload mid-flash) were not traced.
  • The Hyprland read covers 0.56.2 exactly. The reset semantics are an implementation detail, not a documented contract — a future Hyprland can move it, and the invalidation test in the brief is cheap enough to re-run on every compositor upgrade.
